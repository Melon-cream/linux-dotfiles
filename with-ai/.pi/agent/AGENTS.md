# 基本方針

- 日本語回答。
- commit メッセージ・コード内コメント・.gitignore・exampleファイルなど、ドキュメント以外は英語で書く。commit メッセージは 1 行。
- commit時は SKILL git-commit を読む。
- リモート変更（push 等）→ 人間実施。自分は gh 実施可能範囲のみ。
- まず README.md 確認。リンク済ドキュメント全確認。
- コード検証等 → 専用エフェメラルコンテナ (podman) で実施。
- コード読まず書かない。既存コード確認必須。
- 詰まったらWeb検索も実施する
- 変更必要箇所のみ。影響範囲最小化。
- 動作証明までタスク完了マーク禁止。テスト・lint・型検査実出力 証拠提示。
- PR 作成前 → リポジトリ PR テンプレート（`.github/pull_request_template.md` 等）確認。存在時 本文反映。

# 重要：作業の進め方

1. タスク 3 ステップ以上 or ツールコール多数（ドキュメント・レポート含む）→ 着手前に pi-phase で .phases に計画を書き出し (phase.md + notes.md)。それ以外はチャットで方針説明。
  - ユーザー提示のPLANファイルと pi-phase は別スコープのため、必ず作成すること。
  - **勝手に作業を始めない** 実装は、ユーザーが /phase-approve を実行したことを検知してから開始する。検知 = 「phase approved: ...」の通知確認、またはユーザーの明示的な申告。計画作成・提示のみでは実装を開始しない。
  - 計画ファイルの配置は `.phases/YYYY-MM-DD-<slug>/` 配下 (phase.md / notes.md / tasks.json) とする。phase.md は `### Phase N:` 形式のフェーズを含める。`.phases/` 直下への直接配置は拡張機能が認識しない (no active phase: phase.md not found になる)。進捗は phase.md のフェーズ状態を pi-phase のタスク (phase_create / phase_list / phase_get / phase_update) で管理する。タスク状態の変更は phase.md の状態行に自動反映される。
  - セッション中に新規作成したプランは自動でアクティブ化される (通知「new phase detected — auto-selected」、/phase-select 不要)。phase_create で phase 番号を指定すると phase.md のフェーズ見出し (### Phase N:) が自動追加される。
  - 注入コンテキストに「next:」(次に着手すべきタスク) と「stale:」(24h 以上更新のない in_progress タスク) が含まれる。phase_list は description の先頭 60 字を表示する。
  - .phases は gitignore に含める (commit 対象外)。
2. 計画ファイル (phase.md) を作成しない場合でも、実装前にユーザーの承認 (明示的な OK / 実行指示) を求める。承認なしで実装を開始しない。
3. 進行応じて更新

# 知見・memory

- Notion 記録 → ユーザー提案。実際記載はユーザー明言時のみ実施。

## 委譲 (Delegation)

- subagent は subagent ツールで起動する（`pi -p` 別プロセス起動は使わない）。
- 実装タスク以下全条件満たす場合 subagent 委譲可:
  - 実装計画・受け入れ条件 ドキュメント明文化済み
  - テスト・lint・型検査で決定論的検証可
  - 外部システム対話的アクセス不要
  - 自分 (親) 同時に同一ファイル編集しない
- レビュー委譲: 中規模以上 → subagent (reviewer) 起動（→ [レビュー運用](#レビュー運用)）。

# シナリオ A: 大規模開発（新機能・新規プロジェクト）

設計から本番監視まで。各ステップ 前段成果物 入力。

1. **発想検証** — 前提・要求を疑い、設計方針 明文化。
2. **仕様化** — 曖昧な意図 → 実行可能仕様化、Issue 化。
3. **設計レビュー（承認ゲート）** — 設計内容 第三者視点（アーキテクチャ・保守性・DX）確認。
4. **実装計画** — 2〜5 分粒度、テスト先行順序、正確なファイルパス・コマンド含む計画作成。テストステップ無きタスク → 不完全 差し戻し。
5. **作業環境の隔離** — → [ブランチ・worktree 運用](#ブランチworktree-運用)。
6. **実装** — テスト駆動開発（RED → GREEN → REFACTOR）。テスト先行。実装先行書いた場合 → 破棄 やり直し。
7. **完了確認** — テスト・lint・型検査実出力 証拠確認。
8. **コード審査** — subagent (reviewer) 起動による別視点レビュー（→ [レビュー運用](#レビュー運用)）。UI 変更あり → 視覚的 QA 実施。認証・入力処理・権限 触れた場合 → セキュリティ観点レビュー追加。
9. **QA** — 主要利用シナリオ・エッジケース 実動確認。性能関連変更 → 計測 裏取り。
10. **出荷** — テスト・CHANGELOG 更新・commit 実施。push 人間。
11. **記録** — ドキュメント更新、プロジェクト固有学び 残す。

**使わないもの:** 本シナリオ 軽量発想確認・設計レビュー重複させない。

# シナリオ B: 小規模作業（機能追加・不具合修正）

「1 PR に収まる規模」目安。

## 不具合修正

1. **原因特定** — 実行環境・実データ絡む場合 実動調査。純ロジック・テスト失敗のみ → 体系的原因分析（仮説→検証繰り返し）。いずれも**調査なし修正禁止**。3 回修正失敗 → 手を止め、設計レベル見直しへ切替。
2. **再現テスト** — 失敗テスト先行作成、実落ち確認（RED）。
3. **修正** — テスト駆動開発 GREEN。
4. **検証** — 再現テスト GREEN・既存テスト非破壊 出力提示。
5. **審査** — 規模判定。中規模以上 → subagent (reviewer) 起動（→ [レビュー運用](#レビュー運用)）。**commit**。

## 小さな機能追加

1. **設計確認** — 軽量。判断割れる点のみ確認。
2. **実装** — テスト駆動開発。テスト先行厳守。
3. **検証** — 規模判定。中規模以上 → subagent (reviewer) 起動（→ [レビュー運用](#レビュー運用)）。**審査 → 出荷**。

**格上げ条件:** 外部 API 契約変更、DB スキーマ変更、認証・課金影響 → シナリオ A。

# シナリオ C: ドキュメント作成

ドキュメント テスト駆動開発非適用。代わりに**事実整合性**検証。裏取り不可記述 書かない。

## C-1: 既存コードを記述する場合

1. 記述対象コード必読。動作未確認内容 書かない。
2. コマンド例・API シグネチャ・パス・設定値 → 実行 or grep 裏取り。

## C-2: 調査してまとめる場合（技術調査・比較検討・提案書）

1. **アウトプット定義** — 読み手・「この文書で何を判断するか」先に確定。曖昧なら要求確認。
2. **調査計画** — 調査項目 計画ファイル書き出し、出典付き所見蓄積。調査 往復発生 → 記録なし 結論根拠 見失う。
3. **情報収集**
   - リポジトリ内 → 検索・grep 網羅確認。
   - 外部情報 → 公式ドキュメント・一次情報優先。ブログ等二次情報 → 一次情報で裏取り。
   - 独立調査項目複数 → 並列化検討。
4. **裏取り** — 主張 1 つ 出典 1 つ以上。バージョン・日付明記。実行可能コマンド・API → 実動確認。
5. **不確実性明示** — 確認不可点「未確認」明記。推測 事実として書かない。
6. **設計提案含む場合** — 前提・トレードオフに反論する視点で見直し。

## 共通

記述内容・実装・根拠 齟齬 → レビュー確認後 commit。

# ブランチ・worktree 運用

- main 直接作業禁止。作業ブランチ作成後 開発。
- **local ブランチは外部公開しないが、開発記録の全履歴を記録する場所として保持し、削除しない。** main への squash 統合後も local ブランチは残す (開発履歴の保全)。
- 並列作業 → git worktree 等で作業領域分離、コンフリクト防止。
- 実装完了・テスト通過後 → 統合方針（マージ／リベース／squash 等）リポジトリ慣習に合わせ決定。

# レビュー運用

**規模判定と subagent 起動トリガー:**

| 規模 | 判定基準 (いずれか該当) | レビュー |
|---|---|---|
| 小 | 変更 1〜2 ファイル・200 行未満・内部ロジックのみ | 自己レビューで可 |
| 中 | 変更 3 ファイル以上 or 200 行以上 or 複数モジュール跨ぎ | **subagent (reviewer) 起動必須** |
| 大 | 設計変更・アーキテクチャ影響・複数機能横断 | **subagent (reviewer) 起動必須** |

**格上げ条件** (規模に関わらず中以上へ): DB スキーマ / 認証・権限 / 外部 API 契約 / 並行処理 / エラーハンドリング変更。

**手順:**
1. 実装完了・検証 GREEN 後、`git diff` で規模判定。
2. 中規模以上 → **subagent (reviewer) を必ず起動**し未コミット diff をレビュー。
3. 指摘解決 or 明示的対応判断後 commit。

**指摘対応** — 指摘 無批判実装禁止、技術的検証後対応。不明瞭・technically questionable 指摘 → 根拠確認。同意パフォーマンス・盲目的実装 禁止。

# 作図

- 簡単な図 → mermaid インライン記述。
- 複雑な図（アーキテクチャ図・ER 図・ネットワーク図・シーケンス図・ワイヤーフレーム）→ 専用作図ツール・フォーマット（drawio 等）検討。

# コマンド運用

- GitHub 操作（PR 作成・レビュー、Issue 管理）→ `gh`
- git リポジトリ操作（コミット・ブランチ・マージ）→ `git`
- コマンド未検出 → 該当パッケージマネージャ（`mise`, `npm`, `pip` 等）導入試行。
- web 系開発 → 動作検証 に playwright-cli スキル利用。
- コンテナ → podman 利用。

# コーディング規則

- 関数型アプローチ優先、副作用最小化。
- 厳密型付け意識。
- エラー握りつぶさず、意味あるメッセージ付き処理。
- YAGNI / DRY 遵守。計画外機能追加禁止。

# CI/CD

ユーザー要望時のみ作成。workflow 以下ルール従う。

## ルール

- ビルド workflow → タグのみトリガー。
- ドキュメント作成 → トリガー除外 (path 回避)。

## 成果物

1. push 時実行 Lint / Format チェック workflow。
2. CHANGELOG.md 該当バージョン内容抽出 → Release ノート挿入 workflow。
   - prepare-release に、タグから得た version で CHANGELOG.md 該当セクション抽出 step 追加。
   - リリース action に抽出結果 body 渡し、Release 作成時点 本文確定。
3. docker 前提 → 自動ビルド・push workflow。
4. docker 前提でない → バイナリビルド → releases 含める (windows 対象外)。
